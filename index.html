Exercise 1 — Spec-Driven Development

Build a command-line temperature anomaly detector from scratch using a disciplined, spec-first workflow. You will iteratively develop a specification through conversation, critique it, plan an implementation, and then build it with AI assistance.

The Problem

Create a CLI tool that reads a CSV of daily temperature readings, detects anomalies (days more than 2 standard deviations from a 30-day rolling average), and outputs a list of flagged dates, deviation magnitudes, and an ASCII chart. The tool must validate the schema, handle missing values explicitly, and include tests.

Data
📊 temperature.csv
Prompts

Use these prompts in sequence with Claude or another AI coding agent.

Prompt 1 — Gather Requirements

Ask one question at a time to iteratively develop a thorough, step-by-step specification.

Ask me one question at a time so we can develop a thorough, step-by-step spec for this idea. Each question should build on my previous answers, and our end goal is to have a detailed specification I can hand off to a developer. Let's do this iteratively and dig into every relevant detail. Remember, only one question at a time.
Prompt 2 — Compile Specification

Consolidate the conversation into a developer-ready specification document.

Now that we've wrapped up the brainstorming process, can you compile our findings into a comprehensive, developer-ready specification? Include all relevant requirements, architecture choices, data handling details, error handling strategies, and a testing plan so a developer can immediately begin implementation.
Prompt 3 — Critique the Specification

Have the agent act as a senior architect and identify gaps, ambiguities, and risks before implementation.

You are a senior software architect reviewing a developer-ready specification for an agentic coding system. Evaluate whether the specification is: Clear, Complete, Consistent, Correct, Testable, and Unambiguous. Identify missing requirements, ambiguities, inconsistencies, hidden assumptions, edge cases, and testability weaknesses. For each issue: quote the problematic section, explain the risk, and propose a precise improvement. Conclude with a readiness assessment. [Attach specification.md]
Prompt 4 — Build the Implementation Plan

Generate a step-by-step blueprint broken into small, TDD-friendly implementation prompts.

Draft a detailed, step-by-step blueprint for building this project. Break it into small, iterative chunks that build on each other. From here, provide a series of prompts for a code-generation LLM that will implement each step in a test-driven manner. Prioritize best practices, incremental progress, and early testing. Each prompt should build on the previous prompts and end with wiring things together. [Attach specification]

Exercise 2 — Red-Teaming Code

Use Claude Code as a code reviewer. A deliberately flawed codebase contains six intentional issues spanning security, error handling, test quality, and project hygiene. Your job is to prompt the agent, judge its findings, and then use it to apply fixes.

Known Issues
#IssueCategory
1requirements.txt instead of pyproject.tomlToolchain compliance
2SQL query built with f-string formattingSecurity (injection)
3Bare except: pass swallowing errorsError handling
4Missing type hints on public functionsCode standards
5Test that passes but asserts the wrong variableTest quality
6No .gitignore — venv/cache would be committedGit hygiene
Tasks
1. Agent Review

Prompt Claude Code with:

Review this codebase against AGENTS.md for compliance. Check for: security issues, exception handling problems, test quality, dependency management, type hint coverage, and Git hygiene. For each issue, explain the risk and provide the exact file and line number.
2. Manual Verification

Read the agent's findings and cross-reference with the code. Did it catch all six? Did it miss any? Did it flag anything that is actually fine (false positive)?

3. Fix

Ask the agent to fix the highest-severity issue: apply the fix, run tests, and commit. Alternatively, enter planning mode, review a plan to fix all issues, then execute it.

4. Approval Gating

If the fix requires a dependency change, observe the approval gate in action — the agent should pause and ask before installing anything.

Alternative: use /simplify or /review in Claude Code to launch subagents for code reuse, quality, and efficiency review.

Exercise 3 — Model Context Protocol (MCP): Context7

Configure Context7 for your coding agent and use it to retrieve current library documentation. Context7 exposes documentation through MCP, allowing your coding agent to look up current APIs and examples rather than relying entirely on its trained knowledge.

1. Utilize a coding agent without Context7
  1. Ask your coding agent: "What MCP servers and tools do you currently have available?"
  2. Review the output
  3. Ask your coding agent: "Show me how to create a Python validation model using the current version of Pydantic. Include one field validator."
2. Install Context7
Context7 requires Node.js 18 or later. If necessary, install Node.js at https://nodejs.org/en/download.

From a terminal, run the following commands to install Context7 and start the server: 
npx ctx7 setup
Follow the prompts and:
  1. Select MCP Server
  2. Select your coding agent
  3. Complete the authentication process
3. Use the coding agent with Context7
Ask your coding agent: 
Using Context7, retrieve the current Pydantic documentation and show me how to create a model with one field validator. Tell me which documentation you used before writing the code.
4. Review
  1. How did the coding agent answer the question without Context7?
  2. How did the coding agent answer the question with Context7? Was it necessary to directly reference Context7?
  3. What are the advantages of using Context7 with your coding agent?
  4. What are the disadvantages of using Context7 with your coding agent?
  5. Why might retrieving documentation be preferable to simply increasing the size or capability of the model?
  6. What could still go wrong even when the agent has access to authoritative documentation?

Exercise 4 — Install and Use an Agent Skill

Time: 10–15 minutes

Install a small reusable skill into your coding agent and observe when the agent chooses to use it.

1. Create the skill

In your working directory, create a file named SKILL.md:

---
name: change-review
description: Review a code change for correctness, tests, error handling, and unnecessary complexity. Use when asked to review a diff, patch, or recently modified code.
---

# Change Review

When reviewing a code change:

1. Examine the change before proposing modifications.
2. Look for correctness problems and edge cases.
3. Identify missing or weak tests.
4. Check error handling.
5. Flag unnecessary complexity.

Return:

## Findings
Problems that should be addressed.

## Tests to Add
Tests that would improve confidence.

## Suggestions
Non-critical improvements.

Do not modify the code unless the user explicitly asks you to.
2. Install it

Choose the agent you are using.

Claude Code
mkdir -p .claude/skills/change-review
cp SKILL.md .claude/skills/change-review/
Codex
mkdir -p .agents/skills/change-review
cp SKILL.md .agents/skills/change-review/
Gemini CLI
mkdir -p .agents/skills/change-review
cp SKILL.md .agents/skills/change-review/
GitHub Copilot
mkdir -p .github/skills/change-review
cp SKILL.md .github/skills/change-review/

Copilot also recognizes .agents/skills, so the Codex/Gemini version can often be reused unchanged.

3. Test automatic activation

Give the agent a normal request:

Review the changes I have made to this project.

Do not mention the skill. Observe whether the agent discovers and uses the skill from its description.

4. Test explicit activation

Now explicitly request it:

Use the change-review skill to review my changes.

Compare the result.

5. Change the skill

Add this instruction:

Classify every finding as BLOCKING or NON-BLOCKING.

Run the same review again.

Discuss

What changed?

  • Did you have to restart or reload the agent?
  • Could you tell when the skill was activated?
  • How much behavior came from the model versus the skill?
  • Is this better placed in a skill or in CLAUDE.md, AGENTS.md, GEMINI.md, or repository instructions?
  • What parts of this skill could be shared across coding agents?
